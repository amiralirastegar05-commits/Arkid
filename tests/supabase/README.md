# Synthetic Supabase integration

`.github/workflows/synthetic-supabase.yml` starts an unlinked local Supabase stack in a GitHub-hosted runner with no repository secrets. It installs migrations 001–010 on the disposable database and uses three synthetic accounts against actual local GoTrue and PostgREST. It tests profile isolation and opt-in discovery, teams, block/unblock, reporting and moderator access, snapshot isolation, and the actual ranked Worker source against local Auth and REST. The test script refuses any API base other than `http://127.0.0.1:54321` and requires an explicit local-only flag. No browser or hosted Supabase or Cloudflare service is covered by this test. The exact atomic 003–010 stage plus server-side reporting hold is also tested, with reporting temporarily enabled only in the disposable stack for moderation tests and then held again. A passing run is recorded at https://github.com/amiralirastegar05-commits/Arkid/actions/runs/44730733455.

An additional synthetic backup/restore rehearsal is included. It makes local-only CLI dumps, destroys only the disposable local cluster, restores into a fresh local database, compares selected synthetic row counts and exercises the reconstructed signup trigger. Its standard `postgres` restore failed on `log_min_messages`, while an explicitly verified local superuser succeeded after a separate, known `auth.users` trigger was recreated; see run https://github.com/amiralirastegar05-commits/Arkid/actions/runs/44729471319. The default schema dump excluded that managed-schema trigger. The real project has the same trigger according to a read-only catalog check, but its own encrypted backup still failed the isolated restore; this synthetic result does not prove real or hosted recovery. Do not blindly execute the local superuser or trigger procedure on production. Supabase-managed configuration, Storage objects, and consistency of separate dumps need independent consideration.

The workflow runs only for the fixed session branch and an explicit commit subject beginning `Run local Supabase test [approved]`. It has no scheduled or PR trigger; it uses synthetic credentials generated by the local CLI only. Supabase CLI and Docker are needed; the ordinary `npm test` suite does not start this stack.
