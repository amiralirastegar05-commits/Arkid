# Arkid cloud migration audit and rollout

This is an audit of the tracked static hub, individual games, service worker/PWA assets, auth UI, Worker and SQL migrations at the phase-1 base. It is not an audit of the live Supabase/Cloudflare configuration: this environment has no project access. No production migrations, Worker deploys or data changes were performed.

## Current architecture and findings

- `index.html` is the hub and owns the points/XP economy; the standalone game HTML files have separate saves and economies. `auth.js` and `cloud/arcade-auth.js` provide account login, not cloud progress. Supabase browser keys are publishable keys, not service-role credentials. The Supabase library is loaded from esm.sh, so login and cloud features need that CDN and the network. Existing offline gameplay remains independent of login. The PWA service worker caches same-origin assets, not that external library. Many game pages try to register blob/data service workers; browsers generally reject those URLs, so offline availability depends on the hub's `sw.js` and previous caching. Cache install uses `Promise.allSettled` and may succeed even if some assets failed. Test offline per game on real devices.
- The Worker has only `/health` and `/v1/me`; cloud snapshots use Supabase directly, not the Worker. The former health page read `status` while the API returns `ok`; it also skipped the health test if the auth module failed to import. Both are fixed. `/health` now allows public cross-origin GET without credentials; it cannot prove Auth or `/v1/me` works. The authenticated route still strictly allowlists exact origins. The checked-in allowlist permits GitHub Pages and **only** `http://localhost:8787`; another local port, `file:` (origin `null`), a preview origin, a custom domain, or a deployed Worker with different/stale variables will fail preflight. Missing Worker key or wrong project causes `/v1/me` failure. A network/429/5xx Auth failure now returns 503 rather than 401. Outbound restrictions prevented testing the live endpoint, so the deployed root cause is not confirmed.
- Migrations 001–003 create or extend profiles, but `CREATE TABLE IF NOT EXISTS` does not retrofit every column/constraint onto an existing incompatible table. Trigger creation only creates profiles for *new* Auth users; `getProfile().single()` can fail for older users without a row. Migration 005 limits the known profile select policy to self and limits update privileges to the four reviewed fields. Before applying, inspect the live schema, other permissive policies and column grants: PostgreSQL policies are ORed, and existing legacy grants/policies can defeat the intended restrictions. Verify those columns exist and that no other application depends on public profile reads.
- The old developer export captured every origin key, including Supabase session tokens; exports now exclude session/PKCE keys and cloud binding. Imports preserve the current session/binding and ignore those keys in old backup files. Import invalidates the local cloud revision. Existing developer import is a **destructive full replacement of other local keys**, not a merge; the user must first export a full local backup. Local memory fallback now overrides stale persistent values in the export. The backup can still contain private game/profile data; treat it as sensitive.
- Local balances and claim flags are client-controlled and can be edited with developer tools. This change does **not** implement a server-authoritative economy, anti-cheat, cross-device transaction ledger, or public leaderboards. Replaying an older save manually can repeat rewards; revision checks do not make the economy authoritative. Do not use these balances for real-money or competitive decisions.

## Snapshot protocol and safe use

The player explicitly uploads from the account dialog. The first upload only creates a cloud snapshot when no remote snapshot exists. Afterwards, per-browser metadata binds the progress to that account and cloud revision. A server-side advisory lock and compare-and-swap reject concurrent/stale writes; previous revisions are retained in a private history table. If an upload response is lost, the next attempt compares the complete data and adopts the existing revision when identical rather than making another write. Divergent devices are a conflict: no automatic merge or overwriting occurs. This is manual backup/transfer, **not automatic background sync**; no transactions are replayed. Local play continues offline.

For first migration, close all other Arkid/game tabs, sign in, export a local backup if possible, and choose the account-dialog cloud backup button. Every upload is explicit. To restore on another device, open `cloud/restore.html` **before opening the hub**, sign into the same account, close all other tabs and restore. Restore only works when no recognized game key already exists; it never replaces or deletes existing game keys, preserves auth/unrelated keys, and attempts to roll back partial writes on storage errors. If the hub has initialized defaults, restore may refuse even on an apparently new browser. Use a fresh browser profile; do not clear existing data without first backing it up. The restore page can download the cloud snapshot for inspection or manual recovery; importing that file via the developer panel is destructive and requires a prior full local backup.

Conflicts deliberately have no one-click winner: keep/export both versions and resolve manually after review. The server retains previous cloud versions in `arkid_cloud_snapshot_history`, but there is no history browsing UI yet. No automatic per-field conflict resolution is possible with legacy data: timestamps are not reliable and taking maximum balances or summing counts can undo purchases or duplicate claims. Browser storage is shared across accounts, so switching accounts with an existing cloud binding is blocked rather than silently uploading someone else's data. The binding itself is local and can be removed by browser storage clearing or external tools; the system cannot detect all manual rewinds or concurrent legacy writers. Close other tabs, and do not treat this as a multi-writer transaction system. Browsers with disabled/full storage, in-memory fallback or downloads blocked by embedded browsers need special care. Rollback can itself fail if storage becomes inaccessible.

## Deployment checklist

1. Back up the live database and player data. Review 004/005 against the real Supabase schema, roles, existing grants and policies; apply in order after 001–003 in a staging project first. Confirm PostgREST exposes the new tables/function and test two test users and two devices. Profile policy tightening is an intentional compatibility change. No service-role key belongs in the client or repository.
2. Deploy the Worker from `worker/` with `SUPABASE_URL`, the **publishable** `SUPABASE_PUBLISHABLE_KEY`, and exact comma-separated frontend origins in `ALLOWED_ORIGINS`. `localhost:8787` is the Worker port, not necessarily the static frontend port. Never use a wildcard for authenticated routes. Then deploy the frontend and ensure the new service worker activates; old caches can serve old code until update. The health endpoint is intentionally public; check `/v1/me` separately with a user token and browser preflight from the actual frontend origin.
3. Configure Auth redirect URLs, Google OAuth and SMTP as described in `AUTH_SETUP-fa.md`. The restore page supports email/password or an already established session; Google-only users currently need an existing session. Verify CDN, email/OAuth callbacks, refresh/sign-out and mobile embedded browser behavior.
4. Test offline startup/gameplay, first upload, empty-browser restore, divergent device rejection, sign-out/account switch, network interruption, concurrent uploads, storage quota, cache upgrade and legacy backup recovery on staging. Cloud snapshots may contain profile names and gameplay data: configure retention, backups, user deletion/privacy policy and abuse/rate/storage limits. History grows on every successful update; it is intentionally not automatically deleted.

## Tests

Run `npm ci && npm test` with Node 22. Tests exercise Worker CORS/auth behavior, snapshot validation/conflicts/retries/rollback, and migrations/RLS/CAS in PGlite (PostgreSQL WASM with mocked Supabase Auth roles). They are not a substitute for live Supabase/PostgREST, real concurrent transactions, Cloudflare deployment, a browser end-to-end test or gameplay verification.
